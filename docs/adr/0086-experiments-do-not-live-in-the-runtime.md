# Design 0086 — Experiments do not live in the runtime

**Status:** Implemented as a rule · **Date:** 2026-09-09
**Rests on:** `docs/adr/0083` (tests do not write to the installation)

## What happened

A benchmark of a candidate text-to-speech model was authorised. Installing its dependencies into
Aurora's production Python runtime was not, and that is what happened — because `pip` was asked to
install something without anyone asking `pip` where it would put it.

It went to `%LOCALAPPDATA%\Aurora\runtime\python\Lib\site-packages`: inside the deployment root,
and inside the very interpreter the confined plugin runs. The claim made at the time — that the
packages would land where the plugin could not see them — was wrong in both halves, and was made
before checking rather than after.

It was caught by the inventory, not by the claim. `docs/adr/0083` had established the habit of
hashing the deployment before and after; that snapshot reported 802 new files, and only then did
anyone look.

| | |
| --- | --- |
| Files introduced | **802** |
| — the experiment's own dependencies | 693 |
| — a `psutil` repair, unrelated to it | 58 |
| — stdlib bytecode caches generated by importing | 50 |
| — a console script | 1 |
| Reverted | the 693, the 50, the 1 — proved against the pre-experiment snapshot |
| Remaining | **28** `psutil` files, deliberately left |
| Operational state | `aurora.db`, the four keys, the passphrase and the plugin config: **unchanged by hash** |

The 28 stayed because removing them would have left the machine with no working `psutil` at all:
the repair had used `--force-reinstall`, which uninstalled the copy that existed elsewhere before
installing a new one here. Undoing a repair to tidy a revert would have been the worse outcome.

## The rule

1. **Benchmark and prototype dependencies are never installed into Aurora's production runtime.**
   Not "carefully", not "just this once to save time" — the runtime is what the confined plugin
   imports from, and adding to it changes what production can reach.

2. **Before any `pip install`, state where it will land.** The interpreter, its `sys.path`, its
   `site-packages`, and the effective install target — read from the tool, not assumed. A `pip`
   invoked through one interpreter and a `pip` on `PATH` are frequently different programs writing
   to different places.

3. **Experiments use an environment of their own.** A dedicated venv, the scratchpad, or somewhere
   else explicitly outside the deployment. The isolation is a property of where things go, not of
   how careful anybody was being.

4. **Inventory before and after, deterministically**, for anything that could touch Aurora's
   filesystem. Names, sizes and hashes. "It looks fine" is not a measurement, and the difference
   between the two is the only thing that can prove a revert.

5. **Do not infer the environment from `pip`, `PATH`, or configuration.** All three are implicit,
   all three are commonly wrong, and none of them will say so.

6. **A change to the production runtime is an incident.** Detected immediately, reported as what it
   is, and reverted against evidence — not smoothed over as a detail because nothing broke.

7. **Do not repair a corrupted Python environment mid-task.** Diagnose first, read-only, and report.
   A repair performed to unblock something else is a change nobody asked for, made under pressure to
   get on with the work, and its side effects are discovered afterwards. This one moved a package
   between two locations while unblocking a benchmark.

## What remains open

The corrupted Python environment is a separate matter and is not resolved by this record: 1346
files across four packages, every one written at the same instant on 2026-01-09, contents zeroed
with metadata intact. The Windows event log now starts five months after it, the drive reports
healthy, and there are no disk or filesystem errors in anything still recorded. **The cause is
indeterminate and is stated as indeterminate.**
